# Skill: error-triage

本番で発生したエラーを収集し、**新規のものだけ**を原因究明して修正 PR にする。

このスキルは**無人実行（定期 Routine / cron）を前提に設計されている**。
無人で走るということは、暴走したときに誰も止められないということである。
Step 1 のガードと「やってはいけないこと」は、対話実行時であっても省略しない。

## Step 0. プロジェクト設定の解決

1. 同ディレクトリに `PROJECT.md` があれば読み込み、その設定を最優先する
2. なければリポジトリの `CLAUDE.md` / `package.json` / CI 設定から自動検出する
3. 検出もできない項目は下のデフォルトに従う

| 設定項目         | 意味                                 | デフォルト                         |
| ---------------- | ------------------------------------ | ---------------------------------- |
| 観測ソース       | エラーをどこから読むか               | 不明なら **停止して報告**          |
| 除外パターン     | 仕様どおりの失敗（＝エラーではない） | 4xx のうち認証・レート制限系       |
| 1 回あたりの上限 | 1 実行で修正 PR にする件数           | **1 件**                           |
| 検証コマンド     | lint / typecheck / test              | `package.json` の scripts から検出 |
| ブランチ命名     | 修正ブランチの接頭辞                 | `fix/auto-triage-<fingerprint>`    |
| ラベル           | 起票する Issue / PR に付けるラベル   | なし                               |

**観測ソースが解決できない場合は何も推測せず停止する。** 存在しないログ API を
叩こうとして失敗を繰り返すのが、このスキルで最も起きやすい事故である。

## Step 1. 実行ガード（最初に必ず通す）

無人実行では、以下のガードが「1 件の障害で PR が 50 本立つ」事故を防ぐ唯一の防波堤になる。

**ここで判定するのは全体に関わる 2 つだけ**（指紋ごとの判定は、指紋が確定する Step 4 で行う）:

1. **多重起動の抑止** — 自動起票された open な PR を数える。
   PROJECT.md の上限（デフォルト: **3 本**）に達していたら、ログ収集にも進まず、
   「滞留中の PR がある」とだけ報告して終了する。
   人間がレビューを捌けていないのに PR を積み増しても価値は増えない。
2. **1 実行 1 件** — 1 回の実行で修正 PR にするのは、原則として最も重大な **1 件**のみ。
   残りは検出済みとして記録するだけにする。

## Step 2. エラーを収集する

PROJECT.md で定義された観測ソースから、**直近ウィンドウ**のエラーを取得する。

「前回実行時刻」は保持していない（毎回まっさらなセッションで始まるため）。
代わりに**実行間隔より少し広い固定ウィンドウ**を使い、重なった分は Step 3 の
指紋突合で落とす。取りこぼしより重複のほうが安全である。

- ウィンドウ幅は PROJECT.md の指定に従う（実行間隔の 1.3〜1.5 倍が目安）
- ソースが複数ある場合（サーバーログ / クライアントのエラートラッカー等）は**すべて**見る
- 収集の時点では絞り込みすぎない。件数・発生時刻の分布は重大度判定の材料になる

### 除外（エラーではないもの）

以下は**アプリケーションの正常動作**であり、トリアージ対象にしてはならない:

- 認証されていないリクエストへの 401 / 403（＝認可が正しく効いている証拠）
- レート制限による 429（＝スロットリングが正しく効いている証拠）
- クライアントの不正入力に対する 400 系バリデーションエラー
- ユーザーのネットワーク切断・タブクローズ由来の中断
- 外部 API 側の一時的な 5xx / タイムアウト（自リポジトリのコードでは直せない）

ただし **例外がある**: 機械（cron / バッチ / 外部サービスからの Webhook）が呼ぶ
エンドポイントの 401 / 403 は**異常**である。呼び出し側の資格情報が壊れており、
定期処理が黙って止まっていることを意味する。ユーザーからは「いつのまにか動いていない」
としか見えず、最も気づかれにくい障害なので、**除外せず high として扱う**。
「人間のクライアントが叩くエンドポイントか、機械が叩くエンドポイントか」で判断すること。

PROJECT.md の除外パターンは、この一般則に**優先する**。

## Step 3. 指紋化して重複を排除する

同じ原因のエラーが 1000 件あっても、直すべきバグは 1 つである。

**指紋（fingerprint）** = 発生箇所 + エラー種別 + 正規化したメッセージ から作る短いハッシュ。
メッセージ内の可変部分（ID・UUID・タイムスタンプ・数値・パス引数）は正規化してから
ハッシュを取る。そうしないと同一バグが毎回別物として起票される。

指紋ごとに以下を集計する: **発生件数 / 初回発生 / 最終発生 / 影響エンドポイント**。

そのうえで、既存の記録と突き合わせる:

| 突合結果                                                     | 動作                                             |
| ------------------------------------------------------------ | ------------------------------------------------ |
| 同一指紋の open な PR がある                                 | **スキップ**（レビュー待ち。何も足さない）       |
| 同一指紋の open な Issue に `needs-human` 相当のラベルがある | **スキップ**（人間の判断待ち。蒸し返さない）     |
| 同一指紋の open な Issue がある（上記以外）                  | 再発として件数を更新。未着手なら修正に進んでよい |
| 同一指紋の Issue が close 済み                               | **回帰**。その旨を明記して再起票する             |
| 記録なし                                                     | 新規。Step 4 へ                                  |

記録は Issue 本文にコメント形式で埋め込む（例: `<!-- fingerprint:ab12cd34 -->`）。
無人実行のセッションは毎回まっさらな状態で始まるため、**状態は必ずリポジトリ外部
（Issue / PR）に永続化する**。セッション内のメモや作業ディレクトリのファイルに
状態を持たせてはならない（コンテナごと消える）。

**再発件数の更新は、新規コメントの追加ではなく Issue 本文の編集で行う。**
このスキルは何度も繰り返し実行される。毎回コメントを足すと、数日で Issue が
自分の投稿で埋まり、人間が読めなくなる。**同じことを二度書かない。**

## Step 4. トリアージ（自動修正の対象を選ぶ）

重大度を判定し、対応方針を決める。

| 重大度 | 目安                                               | 動作                     |
| ------ | -------------------------------------------------- | ------------------------ |
| high   | 主要機能が使えない / データが壊れる / 継続的に多発 | 修正 PR を作る（最優先） |
| medium | 特定条件で失敗する / 回避可能 / 散発               | 修正 PR を作る           |
| low    | ログノイズ / 影響が観測されない                    | Issue 起票のみ           |

### 再挑戦の打ち切り（指紋が確定した今、ここで判定する）

修正対象の候補を選んだら、着手する前に**その指紋の過去の自動修正**を確認する。
同一指紋の PR のうち **merge されずに close されたもの**を数える
（＝過去の自動修正が人間に棄却された回数）。PROJECT.md の上限（デフォルト **2 回**）に
達していたら、その指紋は自動修正しない。Issue に「自動修正が繰り返し棄却されている」と
記録し、人間の判断を仰ぐラベルを付けて次の候補へ移る（候補が無ければ終了）。

**merge 済みの PR は回数に数えない**（一度直ったものが再発したなら、それは新しい問題である）。

### 自動修正の対象にしないもの

以下は Issue 起票にとどめ、人間の判断を仰ぐ:

- 原因がリポジトリ外にあるもの（外部 API の仕様変更・障害、インフラ、依存の脆弱性）
- **設定・シークレットの不備**（環境変数の未設定、期限切れの鍵、権限設定）。
  コードを直しても直らない。必要な設定を明記した Issue を起票する。
  「設定が無ければフォールバックする」という回避コードを書いてはならない
- 認証・認可・アクセス制御ロジックの変更が必要なもの
- データ移行（マイグレーション）や本番データの修復が必要なもの
- 修正方針が複数あり、どれを選ぶかが**仕様の決定**になるもの
- 再現も原因特定もできなかったもの（**推測で直さない**）

## Step 5. 原因を究明する

`systematic-debug` スキルの手順（症状の固定 → 事実収集 → 仮説 → 切り分け）に従う。
ここでの追加の要点:

- **ログの全文とスタックトレースを読む。** 1 行目のメッセージだけで判断しない
- エラー発生時刻の前後のログを見る（直前のデプロイ・移行・設定変更が原因のことが多い）
- `git log` でその時刻の直前に入った変更を確認する。回帰なら原因コミットを特定する
- **失敗するテストとして再現させる。** 再現できないものは、修正できたことも確認できない。
  重い環境（ローカルのフルスタック起動など）を必要としない最小の単体テストで再現させるのが
  望ましい。それがそのまま Step 6 の回帰テストになる

原因が特定できないまま Step 6 に進んではならない。特定できなければ、
**調査で分かった事実だけを書いた Issue を起票して終了する**。それは失敗ではなく正しい結果である。

## Step 6. 修正して検証する

1. 作業ブランチを切る（PROJECT.md の命名規約に従う）
2. **原因に対する最小の修正**を書く。ついでのリファクタリングを混ぜない
   （無人で作られた PR は、差分が小さいほどレビューされやすく、安全である）
3. **その修正がなければ落ちる回帰テスト**を追加する。これは省略不可
4. PROJECT.md の検証コマンド（lint / typecheck / test）をすべて通す

検証が通らない場合、修正を強引に押し通さない。3 回試して通らなければ、
そこまでの調査結果を Issue に残して終了する。

## Step 7. PR を作る（merge はしない）

PR には**レビューする人間が判断に必要な情報**をすべて入れる:

- 検知したエラー（原文・発生件数・期間・影響範囲）
- 特定した原因（なぜ起きたか。どのコミット/変更が引き金か）
- 修正内容と、その修正を選んだ理由
- 再現手順と、追加した回帰テストが何を守るか
- **確信度**と、レビュー時に特に見てほしい点
- 指紋コメント（`<!-- fingerprint:... -->`）

リポジトリに PR テンプレートがあれば、その見出し構成に沿わせる。

**merge は絶対に行わない。auto-merge も有効化しない。**
自動生成された修正を人間の目を通さず本番に入れることは、このスキルの目的に反する。
CI が緑になったこと、レビュー待ちであることを報告して終了する。

## Step 8. 実行結果を報告する

無人実行では、この報告が人間にとって唯一の可視情報になる。
**何も起きなかった場合も、その旨を必ず伝える**（沈黙は「動いていない」と区別がつかない）。

- 収集したエラー総数と、指紋ごとの内訳
- 新規 / 既知（スキップ） / 回帰 の件数
- 作成した PR・Issue へのリンク
- 自動対応しなかったものと、その理由

## やってはいけないこと

- **本番データベースへの書き込み・マイグレーション適用・設定変更**。
  このスキルの権限はコードの修正提案までであり、本番環境の操作は含まない
- **merge / auto-merge の有効化**
- ログの中身（ユーザーの個人情報、メールアドレス、トークン、在庫や購入の実データ）を
  Issue / PR にそのまま貼ること。**必ず伏せ字にするか、構造だけを書く**
- 再現も原因特定もできていない状態での「たぶんこれだろう」修正
- エラーを握りつぶす修正（`try/catch` で握って握り潰す、条件を握り潰す、
  失敗するテストを skip する）。それは修正ではなく隠蔽である
- 1 実行で複数の指紋をまとめて 1 つの PR にすること（原因ごとに分ける）
- 前回実行と同じエラーに対して、毎回同じ PR を作り直すこと

## 完了条件（Definition of Done）

- 実行ガード（多重起動・件数上限・再挑戦回数）を通過している
- 収集したエラーが指紋ごとに集計され、既存の Issue / PR と突合されている
- 対応した指紋について、原因が**事実に基づいて**特定されている
- 修正には回帰テストが伴い、検証コマンドがすべて通っている
- PR が open されており、**merge されていない**
- 自動対応しなかったエラーについて、理由が記録されている
- 実行結果が報告されている（対象ゼロの場合も報告する）
