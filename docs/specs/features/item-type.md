# Feature Spec: アイテム種別（食料品 / 日用品）

## 概要

housekeeper は当初「食料品の在庫管理」を主眼に設計されており、期限（`expiry_date` /
`expiry_type`）の入力・アラート・カレンダーが UI の中心にある。しかし洗剤・トイレット
ペーパー・電池・掃除用品といった **日用品** は、

- 期限を持たない（または実質的に意味がない）
- 「切らさないこと」（低在庫 / 消費ペース）だけが関心事

という点で食料品と性質が異なる。期限入力欄を毎回スキップさせられ、一覧では期限のある
食料品と混在するため、日用品の在庫管理には使いづらい。

本 spec は **アイテム種別（`ItemType`）= `food`（食料品） / `daily_goods`（日用品）** を
導入し、

1. ダッシュボード（トップページ）で「すべて / 食料品 / 日用品」をタブで切り替えられる
2. 日用品の登録・編集フォームでは期限関連の入力欄を出さない

の 2 点を実現する。

## ユーザーストーリー

- 日用品（洗剤・トイレットペーパー等）を、期限を入力せずに登録できる
- トップページで食料品だけ / 日用品だけを見られる
- 既存のカテゴリ（例:「日用品」「掃除用品」）を日用品としてマークすると、そのカテゴリの
  アイテムがまとめて日用品タブへ移る
- カテゴリの既定に従わない例外的なアイテム（例:「食品」カテゴリに入れた保存用ラップ）は
  アイテム個別に種別を上書きできる

## データモデル

種別は **カテゴリの既定値 + アイテム個別の上書き** の 2 層で持つ。
これは `days_use_after_opening`（開封後使用推奨日数、#752）で既に採用している構造と同じで、

- 既存ユーザーが **カテゴリ 1 件を切り替えるだけ** で配下のアイテムをまとめて分類できる
  （アイテム単位のみだと既存在庫を 1 件ずつ編集させることになる）
- カテゴリ未設定 / カテゴリの既定と異なるアイテムも救済できる

という両立を狙う。

### `categories.kind`

```sql
alter table categories
  add column kind text not null default 'food'
    check (kind in ('food', 'daily_goods'));
```

- `not null default 'food'`: 既存カテゴリはすべて食料品扱いになり、これまでの表示・
  挙動がそのまま保たれる（後方互換）。
- カテゴリ管理画面（`/_auth/settings/categories`）と `ItemForm` のクイック追加から設定する。

### `items.item_type`

```sql
alter table items
  add column item_type text
    check (item_type is null or item_type in ('food', 'daily_goods'));
```

- **nullable**。`null` = 「カテゴリの `kind` に従う」（明示的な上書きなし）を意味する。
  既存アイテムはすべて `null` のまま = 実質 `food` として扱われる。
- `null` と `'food'` は解決結果としては同じだが、意味が違う（前者は追従、後者は固定）。
  カテゴリを日用品に切り替えたときに追従するかどうかがこの差になる。

### 解決規則

`src/types/item.ts` の純関数:

```ts
export const ITEM_TYPES = ["food", "daily_goods"] as const;
export type ItemType = (typeof ITEM_TYPES)[number];
export const DEFAULT_ITEM_TYPE: ItemType = "food";

export const resolveItemType = (
  item: Pick<Item, "item_type">,
  category?: Pick<Category, "kind"> | null,
): ItemType => item.item_type ?? category?.kind ?? DEFAULT_ITEM_TYPE;
```

優先順位は **アイテム個別 → カテゴリ既定 → `food`**。
カテゴリ未設定のアイテムは食料品として扱う（従来挙動の維持）。

## 画面

### ダッシュボード（`/_auth/`）のタブ

検索欄の上に 3 つのタブ（`ItemTypeTabs`, molecule）を置く。

| タブ   | 値（URL `type`） | 表示対象                                 |
| ------ | ---------------- | ---------------------------------------- |
| すべて | `""`（既定）     | 全アイテム（現状と同じ）                 |
| 食料品 | `food`           | `resolveItemType(...) === "food"`        |
| 日用品 | `daily_goods`    | `resolveItemType(...) === "daily_goods"` |

- 既定は「すべて」。デフォルトの見た目を変えないため、および既存のブックマーク /
  戻る・進むを壊さないため。
- 状態は他の絞り込み（`q` / `cat` / `loc` / `expiry`）と同じく **URL の search param**
  （`type`）で保持する。不正な値は `""`（すべて）にフォールバックする。
- 各タブに件数を出す。件数は他の絞り込み（検索・カテゴリ・場所・期限・在庫0非表示）を
  **適用した後** の集合から数える。タブを押した結果表示される件数と一致させるため。
- 種別の解決にはカテゴリ一覧が要る。ダッシュボードは既に `useCategories()` を呼んで
  いるので、絞り込みはサーバー側（Supabase クエリ）ではなく **クライアント側**で行う
  （`expiryStatus` / `hideEmpty` と同じ扱い）。
- アラートバナー（期限・低在庫・消費ペース予測・棚卸し・バックアップ）はタブに
  よらず全アイテムを対象にする。「絞り込みでアラートを消さない」という既存の方針
  （#450 / #618）をタブにも適用する。

### `ItemForm`（新規登録 / 編集）

- カテゴリ選択の直前に **種別セグメントコントロール**（`ItemTypeSelect`, atom）を置く。
  表示値は解決後の実効種別（`values.item_type ?? 選択中カテゴリの kind ?? "food"`）。
- ユーザーがタップすると `item_type` に明示値が入る。タップするまでは `null` のままで、
  **カテゴリを選び直すとその kind に追従する**（例: カテゴリ「洗剤」を選ぶと自動で日用品に
  切り替わる）。一度手で切り替えたら以降カテゴリに追従しない。
- 実効種別が `daily_goods` のとき、以下を **描画しない**:
  - 期限日（`expiry_date`）入力欄と期限 OCR スキャナ起動ボタン
  - 期限種別（`expiry_type`, 賞味期限 / 消費期限）セグメント
- 購入日（`purchase_date`）・開封後使用推奨日数（`days_use_after_opening`）は日用品でも
  残す。日用品にも「いつ買ったか」「開封後どのくらいで使い切るか」は意味があるため。
- 送信時、実効種別が `daily_goods` なら `expiry_date` / `expiry_type` を **null で送る**。
  食料品として期限付きで登録済みのアイテムを日用品に変えたとき、隠れた期限が残って
  期限アラートやカレンダーに出続けるのを防ぐ。

### カテゴリ管理（`/_auth/settings/categories`）

- 追加フォームと編集フォームに種別セグメント（`ItemTypeSelect`、「未設定」なしの 2 択）を
  追加する。
- 一覧では日用品カテゴリにのみバッジを出す（食料品が既定で大多数のため、既定側には
  出さずノイズを減らす）。

## 影響範囲と非対象

- **期限アラート / カレンダー / 通知**: `ItemForm` から日用品として保存すると
  `expiry_date` / `expiry_type` が null になるため、既存のロジック
  （`getExpiryStatus` が `unknown` を返し、`ExpiryBadge` は null を描画、カレンダーは
  `expiry_date is not null` のみ取得）で自然に対象外になる。専用の分岐は追加しない。
- ただし **既存カテゴリを後から日用品へ切り替えた場合**、そのカテゴリのアイテムには
  食料品時代に入力された `expiry_date` が DB に残る。ダッシュボードはこれを表示用の
  派生値として落とす（`dropExpiryForDailyGoods`）ので、一覧の絞り込み・件数・
  期限バッジ・期限バナー・期限クイックチップは一貫して「期限なし」として扱う。
  DB 上の値はそのアイテムを保存し直すまで残るため、**期限カレンダーと通知
  （Edge Function）では引き続き対象になる**。この2箇所の追従は PLANS.md v1.10 の
  フォローアップ扱い。
- **低在庫 / 消費ペース予測 / 棚卸し / 買い物リスト**: 種別に関係なく従来通り機能する
  （むしろ日用品にとってはこちらが主役）。
- **統計 / レシピ / 献立**: 本 spec では種別による絞り込みを入れない。
- **JSON インポート**（`import_items_batch` RPC）: 本 spec では `item_type` を扱わない。
  インポートされたアイテムは `item_type = null`（= カテゴリ追従）になる。

## テスト

- `resolveItemType` の純関数テスト（個別上書き / カテゴリ既定 / 未設定フォールバック）
- `ItemTypeSelect` / `ItemTypeTabs` の Story + 単体テスト
- `ItemForm`: 日用品を選ぶと期限欄が消えること、日用品で送信すると `expiry_date` /
  `expiry_type` が null になること、カテゴリ選択で種別が追従すること
- ダッシュボード: タブで一覧が絞り込まれること、件数が表示件数と一致すること
